# Add-store silent-failure investigation

Investigation only; no application fixes. Fresh branch from main `2ef208c831db2ff6fe386108b72097045d0b9577`. Incident date supplied by owner: November 15, 2026. Production's deployed SHA and the affected phone/session were not available for comparison. **The incident's exact initiating cause is not proven.** The mechanisms below were reproduced against this checkout; ranking reflects fit to the account, not measured incident probabilities.

## Ranked findings and minimal proposed fixes

1. **Confirmed hidden error feedback + server-only validation, highest fit.** `client/src/components/home-add-form.tsx:85-102` accepts any website text and has no description/name/address/product upper bounds. `shared/schema.ts:65-90` rejects bare websites, descriptions >1,000, names >100, addresses >200, products >50 each or >20 total, invalid coordinates, and city/province <2 characters. `api/_lib/server_routes.ts:187-191` returns 400 before persistence. Mutation errors only call a toast (`home-add-form.tsx:204-215`); the outer catch only logs (`265-271`). The global modal is z-index 9999 (`global-add-store-modal.tsx:32`), toast viewport 2200 (`ui/toast.tsx:17`). On 390×844 Chromium, error text is covered by the form, with only a pink strip visible; hit-testing the toast center returns the modal header. Button returns enabled with its original text, no success state. Required fields may all be valid. Reproduce: open Add a store; enter `TEST Épicerie d'Orléans`, `123 rue d'Orléans, Québec, QC G1R 4P5`; select Roshen chocolates; website `example.com`; Submit. Real local route returns 400; persistence stub is not called. Also reproduce with website blank and 1,001-character description, or no selected chips and `,,,` as other products (nonempty before split, empty after split at `home-add-form.tsx:248-251`). Proposed minimal fix: persistent in-modal `role=alert` for every submit exception and mirror server constraints on client; parse/validate final products rather than raw comma text. Optional website normalization should be a deliberate product decision. Raising toast z-index alone does not address timeouts, field-specific guidance, or accessibility.

2. **Confirmed hidden errors after blocked/failed POST, also high fit.** `client/src/lib/api.ts:122-138` awaits POST `/api/locations`, parses JSON on all statuses, and throws. Browser route abort (`failed`), 500, 409, 429, and HTML 502 each return to the unchanged enabled button with covered toast text and no success modal. Test abort guarantees no server request/persistence. Stubbed HTTP failures model a rejection before persistence; they do not prove live Supabase was responsible. A quick failure can make a transient spinner hard to notice; we did not reproduce a handler execution with literally no spinner state. Proposed minimal fix: same persistent in-modal error boundary; robust JSON/text error decoding, actionable network/retry messaging, and safe retry semantics.

3. **Confirmed unbounded awaits, weaker fit because loading IS visible.** Photon fetch and body parse have no timeout (`home-add-form.tsx:175-183`); POST/body parse also lack one (`lib/api.ts:122-138`). Hold Photon pending: zero POSTs, disabled button and spinner still present after three seconds; there is no code deadline. Hold POST pending: spinner stays, no terminal feedback. The server can also wait before insertion on duplicate lookup (`server_routes.ts:218,222`) and DB query; pool configuration has no explicit connection/query deadline (`db_storage.ts:165-168`). REST fallback has no timeout (`db_storage.ts:352-369`). Proposed minimal fix: bounded geocoding and submission deadlines including response-body reads; recover with a specific visible error or the existing documented geocoding fallback. Server DB/query and fallback deadlines must also be bounded. For an ambiguous POST timeout, tell the user outcome is unknown; use an idempotency key before offering blind retries. **Absence of loading does not follow from hanging at the first await: `setIsSubmitting(true)` runs before it.** If the witness truly saw no transient change, investigate the original device, deployed bundle and input/click delivery rather than claiming this proves a hang.

4. **Confirmed fallback-coordinate duplicate hazard, conditional incident relevance.** Empty/failed geocoding substitutes the same Canadian center for every manually entered unresolved address (`home-add-form.tsx:235-240`). Duplicate detection rejects any coordinates within 0.0001 degrees regardless of business name/address (`api/_lib/security.ts:182-211`; route `server_routes.ts:228-229`). Thus after one fallback submission exists, an unrelated fallback submission can get 409 and the covered toast. Reproduce locally by calling the real duplicate helper with two different names/addresses both at 56.1304,-106.3468; result true. This has not been checked against production rows. Proposed minimal fix: don't run proximity-only duplicate rejection for sentinel/unverified coordinates; retain name/address matching and mark unresolved geocoding explicitly.

## Complete submit trace

`GlobalAddStoreModal` listens for open events → `HomeAddForm` → react-hook-form/Zod resolver (`home-add-form.tsx:325`) → valid callback sets submitting immediately (`219-220`) → use existing coordinates or await Photon → failed/empty geocode becomes Canadian-center fallback → split products/derive category → await React Query mutation → `apiCreateStore` POSTs to same-origin `/api/locations` → submission limiter → honeypot → server schema → spam filter → duplicate lookup → `storage.createStore` (status forced `pending` at route line 212) → direct Postgres/Drizzle insert (`db_storage.ts:429`) → on failure service-role Supabase REST insert (`432-433`, `322-369`) → JSON response → `apiStoreToStore` → mutation success sets `isSubmitted` → thanks panel (`home-add-form.tsx:275-280`). Failure in mutation calls toast then rethrows to console-only catch; finally resets submitting. The modal stays open and changes its contents on success; there is no separate success-dialog request.

Google Places autocomplete is optional enrichment, not the submit-time geocoder. Its missing geometry early return (`home-add-form.tsx:142`) doesn't itself block submission; manually typed addresses use Photon. Autocomplete-selected coordinates are not cleared when address text is edited: possible wrong location/duplicate rejection, not a proven silent return.

Photon is controlled. Normal/validation POST cases are forwarded to a localhost Express server running the actual `registerRoutes`, with all relevant storage methods replaced by in-memory stubs **before requests**. Error/hang POST cases are deliberately intercepted. No Supabase or production requests/inserts/deletions occurred. `TEST-memory-only` results exist only in response objects; no persistence to clean up. These are controlled reproductions, not real-phone/Safari or live-provider verification.

## Every silent/incomplete-feedback path found

- Server schema rejection (all limits and sanitization-empty fields above), spam 400 (`server_routes.ts:194-198`), duplicate 409, submission rate limit 429 (`security.ts:126-132`), general API limit (`117-124`), middleware/body-size failures (`app.ts:102-123`), and DB/REST insert rejection → only covered toast. Spam and parser/DB outcomes traced; representative HTTP responses reproduced, not all live conditions.
- Network/CORS/CSP/content-blocker/offline POST rejection → covered toast. Non-JSON or empty error bodies become JSON parser errors rather than specific server errors. Abort reproduced; individual phone/content-blocker configurations not tested.
- Geocoder fetch/body pending → indefinite spinner and no insert. POST fetch/body pending → indefinite spinner; body-only stall follows same unbounded awaits but was not separately injected. Server duplicate reads and direct DB/fallback REST waits can similarly stall the request; not tested against live DB.
- Any exception in submit preparation before `mutateAsync` only reaches the console catch, no toast/inline feedback. No ordinary schema-valid form input was found to trigger such an exception; this is an uncovered error boundary, not a reproduced user-input cause.
- Product validation toast itself is covered, but its inline `FormMessage` is present and visible when scrolled to; this is not wholly silent missing-required validation. Keyboard Enter prevention on non-address/non-textarea/non-button controls (`home-add-form.tsx:334-348`) intentionally suppresses implicit submission with no status; excluded as explanation for explicit Submit taps.
- Honeypot (`server_routes.ts:180-183`) intentionally returns fabricated success with no row; this produces the thanks panel, so it does **not** match no-feedback incident. Autofill could populate it; not proven here.
- Response parse/conversion failure after a successful insert can hide success via covered toast, but may leave a real row. Excluded from the strictly no-row subset. Likewise timeout/retry and double-submit can produce rows or ambiguous outcome.
- Settled Photon exceptions are console-only, but caught and followed by fallback insertion. They are not themselves silent end states. Missing Google Places geometry is also not a submit dead end. Stale coordinates or out-of-Canada Photon results can instead cause server rejection as above.

## Supabase RLS and constraints: verified scope

There is no Supabase connector, DB URL, or server-role credential available in this environment. **Live `Ukraine2026.public.stores` policies, grants, constraints, triggers, and incident logs could not be verified.** `setup_supabase.sql:5-57` defines `locations`, not `stores`, enables RLS and supplies only a SELECT policy; it cannot establish current `stores` insert permissions. Runtime fallback explicitly requires `SUPABASE_SERVICE_ROLE_KEY` (`db_storage.ts:322-331`) and uses it as both apikey and bearer token (`352-359`), rather than anon. Normal path is server-side direct Postgres with the DATABASE_URL role; that role's grants/bypass status are unknown. An absent anonymous-insert policy therefore is not enough to explain this form's failure. Do not weaken RLS as a proposed fix without evidence.

Repository `shared/schema.ts:22-43`: required text name/description/address/city/province/category/status, text[] products, numeric(10,7) latitude/longitude, text PK id, created_at not-null with default, images array with default. Text fields have no database length cap shown; name/description/etc upper limits above are application Zod constraints, not established live DB constraints. No stores RLS migration is checked in. Read-only SQL in `rls-readonly.sql` collects policies/RLS flags/grants/columns/constraints/indexes/triggers when an authorized operator has project access; it has not been executed.

## Proposed acceptance checks (future fixes only)

Every explicit Submit must yield visible progress followed within a bounded time by either thanks or a persistent, specific, in-modal accessible error. Keep entered data on failure. Verify both manual and autocomplete addresses, failure before and during mutation, all server rejection types, stalled fetch AND stalled body reads, offline/blocked requests, and rapid repeat events. Assert the error is actually unobscured, not merely present in DOM. Retest on the affected mobile browser. Correlate incident timestamp/input with function logs to identify whether it was 400/409/429/500/no request; never infer the incident trigger solely from these reproductions.
